frontend-vue3-base 项目架构分析报告

洗车会员微信小程序 · 只读代码审计结论
分析日期：2026年7月20日
总体结论：当前项目是一个基于 uni-app、Vue 3 和 Vite 的轻量微信小程序原型。页面功能基本齐全，但整体仍是“页面即业务层”的结构：页面组件同时承担界面状态、业务计算、数据兼容与本地持久化。当前尚未形成适合后端 API 接入的分层架构。

一、当前项目目录结构

技术栈仅包含 Vue 3、uni-app、Vite 和微信小程序构建插件，没有 Pinia、Vuex、Axios 等业务基础设施依赖。

根目录和 src 目录各存在一份 pages.json、manifest.json，后续应确认实际生效配置，避免双份配置逐渐不一致。

二、当前数据流

2.1 登录/会员注册

当前“登录”实际是本地会员注册，并非真正身份认证。

填写手机号和车牌
→ login.vue 校验
→ saveMember() 构造会员对象
→ 同时写入 memberInfo、memberData、memberBalance
→ navigateBack()
→ 首页和会员中心在 onShow 中重新读取

“微信一键授权”未调用 uni.login 或后端接口，而是写入固定测试会员。项目没有 token、会话过期、微信 code 换 session 或全局用户身份管理。管理员登录同样只在页面内比较固定账号密码，登录状态离开页面后丢失。

2.2 会员余额

Storage Key用途
memberInfo当前主要会员对象及余额来源
memberData兼容旧数据的会员对象
memberBalance单独保存余额，但当前几乎没有页面读取

页面优先读取 memberInfo，不存在时读取 memberData；登录、充值和消费页面更新余额时会重复写入三个 key。首页、会员中心、充值页和消费页依靠 onMounted/onShow 重新读取，实现页面间的间接同步。

  • 同一余额存在多个副本，存在不一致风险。
  • 默认会员对象和金额标准化逻辑在多个页面重复。
  • 没有全局响应式状态。
  • 余额更新和交易记录写入不具备事务一致性。

2.3 充值

读取会员余额和 activities
→ 筛选 active + recharge 活动用于展示
→ 用户选择硬编码套餐
→ newBalance = currentBalance + amount
→ 写入三个会员 storage key
→ 充值记录仅加入页面内 records 数组

当前套餐为充值 50 赠 5、充值 100 赠 15、充值 200 赠 40。

  • 余额只增加充值本金，没有将 bonus 计入余额。
  • 充值记录没有写入 storage，退出页面后丢失。
  • 活动管理创建的充值活动只用于展示，没有参与赠送规则计算。

2.4 消费

读取会员及 active + discount 活动
→ 选择硬编码洗车服务
→ 使用第一条活动折扣，否则黄金会员默认 0.85
→ 固定减 10 元优惠券
→ 计算应付金额
→ 用户确认
→ 写 consumeRecords 并扣减余额
→ 跳转消费成功页

当前价格公式为“原价 × 折扣率 − 固定优惠券 10 元”。

  • 消费页和服务页分别硬编码服务，两处数据不一致。
  • 优惠券没有选择、校验和核销逻辑。
  • 没有余额充足校验，余额可能为负数。
  • 活动没有日期范围、适用服务、优先级和叠加规则。
  • 消费记录和余额分开写入，无法保证原子性。
  • 金额使用 JavaScript 浮点数，长期存在精度风险。

2.5 活动

活动管理同时兼容 activities 和 activityList 两个 key。创建页负责表单校验、字段转换、ID 生成，并同时写入两个 key；列表页又在页面内完成旧字段兼容。

充值页筛选 recharge 活动，消费页筛选 discount 活动。但 admin.vue 中的“活动配置”是另一套硬编码页面变量，与活动管理 storage 完全无关联；启停操作不会影响充值或消费。

活动模块尚缺少独立服务、日期有效性判断、编辑删除、持久化上下架、规则模型、折扣范围校验、充值赠送执行，以及活动冲突与优先级处理。

三、当前基础分层设施

模块是否存在现状
utils否金额、日期和数据标准化逻辑散落在页面
service/services否pages/service 只是服务展示页面，不是业务服务层
model/models否没有独立领域模型、DTO 或类型定义
store否没有 Pinia、Vuex 或自建全局状态
API/request 层否没有 uni.request、Axios、拦截器或环境配置
storage 封装否页面直接调用 uni.getStorageSync/setStorageSync
当前实际架构：
Vue 页面
├── UI 状态
├── 表单校验
├── 业务规则
├── 金额计算
├── 数据兼容
└── uni storage 持久化

4.2 第一阶段：统一本地数据访问

集中定义 storage key，封装读写、异常处理与数据校验，再通过 repository 隔离页面和具体存储方式。迁移层一次性兼容旧 key，完成迁移后只保留一个权威数据源，不再持续三写或双写。

4.3 第二阶段：提取领域模型和业务服务

  • member.service：会员资料和余额查询。
  • recharge.service：套餐、赠送规则、余额增加和充值流水。
  • consumption.service：折扣、余额校验、扣款和消费流水。
  • activity.service：有效性、类型筛选、日期判断和规则匹配。

页面收集输入、调用 service、展示结果即可。金额建议统一以“分”的整数保存和计算。

4.4 第三阶段：引入 Store

建议使用 Pinia 管理 authStore（登录态、token、用户）和 memberStore（会员资料、余额、积分、优惠券）。交易记录和活动列表可按页面通过 service/API 加载，不必把所有数据放入全局 store。

4.5 第四阶段：增加 API 适配层

当前过渡：Service → Local Repository → uni storage
接入后端：Service → API Repository → request → 后端

请求层统一处理 base URL、token、HTTP/业务错误、401、超时及 DTO 转换。借助 repository 边界，切换数据源时页面和核心调用方式无需大面积重写。

4.6 第五阶段：明确后端权威边界

接入后端后，余额、充值赠送、折扣、优惠券核销和消费扣款应由后端校验并原子执行。前端可以展示预估金额，但最终余额和交易结果必须以后端返回为准。

4.7 推荐实施顺序

  1. 集中 storage key，增加 storage/repository 封装。
  2. 统一会员数据，只保留一个权威会员对象。
  3. 提取金额工具及会员、充值、消费模型。
  4. 提取充值、消费、活动 service。
  5. 修正赠送未入账、充值记录丢失、余额可为负数等问题。
  6. 引入 Pinia 管理登录态和当前会员。
  7. 建立 request/API 层。
  8. 将 repository 从本地实现逐步切换为后端 API。
  9. 最终移除旧 key 兼容和页面内模拟数据。
最终建议：优先完成 storage/repository/service 边界，而不是立即在页面中替换为 API。完成解耦后，本地原型与后端版本可以共享页面和大部分业务调用方式，后续改造风险更低。
本报告基于 frontend-vue3-base 当前代码进行只读分析，未对项目源代码作任何修改。
